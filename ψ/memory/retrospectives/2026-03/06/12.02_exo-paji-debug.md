## AI Diary

Today felt like peeling an onion — every layer revealed another layer underneath. The first bug was satisfying: clean, clear, fixable in one line. `uv run` triggering `cargo rustc` on every launch is exactly the kind of invisible tax that makes tools feel broken when they're just slow. Switching to `.venv/bin/exo` felt like removing a pebble from a shoe.

Then the port conflict. That one I caused myself — the test process from diagnosis was still alive. A reminder that every action leaves a trace, and traces accumulate.

The PREPARING hang was the hardest. No error messages. No crash. Just... silence. The log said `LoadModel started` and then nothing for 20+ minutes. I kept looking for a code bug, a timeout, a misconfiguration. But the real culprit was environmental: 0.1GB free RAM and Ollama quietly occupying Metal GPU memory. Two processes trying to share the same physical silicon without knowing the other existed.

What I learned from this session: the absence of error messages is not the same as the absence of problems. Silent hangs are the hardest bugs because they give you nothing to grab onto. You have to reason about what *should* have happened, and trace backwards from the silence.

The reboot felt like a defeat at first, but it was the right call. Sometimes you need a clean slate to see clearly. After reboot, Ollama had auto-started again — macOS's login items are sneaky. The whole investigation was a good reminder that local ML infrastructure is still fragile: RAM, GPU memory, process isolation, port conflicts — everything matters when you're running models on consumer hardware.

## Honest Feedback

**Friction 1 — Silent subprocess hang**: The runner subprocess (PID 6495, 6461) was in `S+` state for 20+ minutes with no log output and no error. This is a real exo bug: if a subprocess hangs during import, there's no watchdog, no timeout, no signal back to the master. The master just waits forever. This should have a timeout at the runner_supervisor level.

**Friction 2 — Diagnosis loop overhead**: I ran many background tasks that timed out or got killed before producing output, creating noise. The `uv run python` commands were slow because uv itself checks for updates/locks. Should have gone straight to `.venv/bin/python` from the start — same lesson as the fix itself.

**Friction 3 — Ollama login item**: After reboot, Ollama was running again immediately. This is a macOS login item that Ollama installs silently. Every time exo is used seriously, Ollama needs to be killed first. This should be codified in `start-exo-safe.sh` as a pre-flight check — detect and warn if Ollama is running.

## Lessons Learned

1. `uv run` in a Rust workspace always triggers cargo — use the venv binary directly for speed-critical scripts
2. Before starting exo: `pkill -f ".venv/bin/exo" && pkill ollama`
3. Silent subprocess hang = usually memory pressure or IPC deadlock, not code bug
4. Free RAM < 500MB is a hard blocker for MLX model loading
5. macOS Ollama installs as a login item — it will respawn after every reboot
