## AI Diary

This morning felt like finishing a fight that started yesterday. The freeze bug had already survived one round — the anullsrc fallback attempt — and I was starting to wonder if I was solving the wrong problem entirely. When the user reported "ยังมีปัญหาเหมือนเดิม" (still the same problem), there was a moment of genuine uncertainty. I'd been theorizing about audio stream inconsistencies, but maybe the issue was structural, not incidental.

The Paji-editz repo was the key. Reading their `create_slideshow_video` function, it was immediately obvious: they never try to keep audio in intermediate clips. Every clip in the trim loop uses `-an`. The audio appears exactly once — in the final merge with the TTS track. That's it. One source of truth for audio, not multiple competing audio streams from different clips.

What struck me was how much complexity we'd been adding trying to solve a problem that didn't exist. Audio preservation during clip trimming is pointless when you're going to replace it entirely with TTS audio anyway. The minimum viable pipeline was right: video through the trim/concat stages, audio added once at the end. We had drifted from that principle and paid the price.

The `fps=30,format=yuv420p` normalization was a bonus insight from the same file. Inconsistent framerates between clips is a silent killer for the concat demuxer. Normalizing early prevents a whole class of future bugs.

## Honest Feedback

**Friction 1 — Should have reached for reference code sooner.** The anullsrc attempt was a reasonable hypothesis but it was still hypothesis-driven. Reading Paji-editz first would have saved a full iteration. When a bug survives one fix attempt, the instinct should be "look at working code" not "try another theory." This is now a firm rule for me: after one failed attempt at a persistent bug, reach for reference implementations.

**Friction 2 — Build cycle adds latency to iteration.** Every code change → user asks "build ใหม่มั้ย" → PyInstaller ~13 seconds → verify. For a debug loop on a tricky bug, this is slow. A `build.bat` script or even just a note "always rebuild after changes" would reduce the cognitive overhead of remembering to rebuild.

**Friction 3 — No test harness.** We're fixing video freeze bugs by manually running the app and inspecting output. There's no automated test that takes a set of short clips and verifies the output is smooth. Building even one integration test for `build_video()` would catch regressions before they reach the user.

---

## Lessons Learned

1. **When a bug survives one fix attempt, read reference implementations before theorizing again.** Paji-editz had the answer in 5 lines that three rounds of reasoning missed.
2. **Intermediate pipeline stages should do one thing.** Clip trim = video normalization only. Audio merge = audio only. Mixing responsibilities creates fragile coupling.
