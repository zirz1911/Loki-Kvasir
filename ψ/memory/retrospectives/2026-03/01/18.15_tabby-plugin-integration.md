## AI Diary

The infinite Tabby window bug was immediately obvious once I thought about it — `process.execPath` in Electron is the Electron binary, not Node.js. I should have caught this during planning. I even wrote in the plan notes "`process.execPath` = Tabby's Node.js binary" — that was a wrong assumption I propagated forward without verifying. Each spawned Tabby tried to connect, failed, spawned another. Classic exponential bomb.

The `BOOTSTRAP_DATA` failure was subtler. The service had `@Inject(BOOTSTRAP_DATA)` in its constructor. If this injection fails, Angular doesn't throw a visible error at module load time — it just silently prevents the APP_INITIALIZER from running. No logs. No error in the panel. Nothing. That's what made "no logs at all" the correct diagnostic signal. I should remember: silent APP_INITIALIZER failure usually means constructor DI failure.

The `BaseTabComponent(injector)` bug was the most interesting. I had the wrong type declarations because our dev dependency was `1.0.163` but Tabby runtime is `1.0.197-nightly`. The typings said `protected constructor()` with no args. The actual runtime constructor called `injector.get(ConfigService)` — so `undefined.get(ConfigService)` → the cryptic "reading 'get'" error. I traced it correctly by reading the actual installed dist file. The lesson: when Electron plugins have version-pinned runtime deps, development typings MUST point to the actual installed files, not npm registry versions.

The `SplitTabComponent` unwrapping issue — I should have caught this earlier. `openNewTab()` wraps everything in a `SplitTabComponent`. So right-clicking a tab header gives the SplitTab, not the inner terminal. The `frontend` check immediately filtered it out. I knew about the wrapping but didn't connect it to the context menu flow. But it ended up not mattering — the user changed direction to in-panel split controls, which is actually more ergonomic.

The split implementation was clean. Tabby's `SplitTabComponent.addTab(tab, relative, dir)` is exactly what we needed. `TabsService.create()` to instantiate without adding to tab list, then manually insert into the split. The `wrapAndAddTab` fallback for bare tabs worked nicely.

Not a failure — the user's new approach is genuinely better — but the pivot could have come earlier if I had asked "does the tab header right-click feel natural?" during planning.

## Lessons Learned

1. **`process.execPath` in Electron is the Electron binary, not Node.js.** Never assume it's a Node.js binary. To spawn a Node.js subprocess from an Electron plugin, use `'node'` and rely on PATH, or find Node.js from `process.versions` + known installation paths.

2. **Silent APP_INITIALIZER failure = constructor DI failure.** When an Angular plugin produces zero logs and zero errors, the most likely cause is a constructor dependency that can't be resolved, which prevents the APP_INITIALIZER from ever running. Diagnose by checking if Settings tab appears (proves module loaded) vs checking if lifecycle logs appear (proves initializer ran).

3. **Dev typings must point to the actual installed runtime, not npm registry.** For Electron plugins, use `"file:path/to/installed"` for ALL host-app dependencies. Version drift between dev typings and runtime is a silent bug factory.

4. **Angular BaseTabComponent in Tabby requires `Injector` in constructor.** Must inject `Injector` and pass to `super(injector)`. The typings may lie depending on version.

5. **`openNewTab()` wraps in `SplitTabComponent`.** Any code that checks tab type or accesses `(tab as any).frontend` must first unwrap via `instanceof SplitTabComponent ? tab.getAllTabs()[0] : tab`.

6. **`TabsService.create()` instantiates a tab without adding it to the tab list.** Use this when you need to create a component instance to manually insert into a split. Use `openNewTabRaw()` when you want immediate tab-bar insertion.
