## Key Code Changes

**CREATE_NO_WINDOW (tray.rs)**
```rust
use std::os::windows::process::CommandExt;
const CREATE_NO_WINDOW: u32 = 0x08000000;

Command::new("powershell")
    .args([...])
    .creation_flags(CREATE_NO_WINDOW)  // ← this was the fix
    .spawn()
```

## AI Diary

Today was one of those sessions that starts simple and keeps pulling the thread. "Statusline ไม่มา" — okay, I thought. Quick debug. Five minutes, maybe ten. But Windows has a way of layering surprises.

First discovery: `python3` in hook commands on Windows hits the Microsoft Store stub silently. A path that works fine in macOS shell just evaporates on Windows without error. Fixed with a full path. Easy enough.

Then came the voice tray window. Every time Kvasir spoke, a PowerShell window flashed. We tried every trick — pythonw, wscript, VBScript wrappers, removing async, adding async back. The window kept appearing. I kept telling Lokkji "this should work" and it kept not working. There's something humbling about that. The confidence draining out with each "ยังมีเหมือนเดิม."

The real culprit was hiding in `tray.rs` the whole time — `Command::new("powershell")` spawning without `CREATE_NO_WINDOW`. Not `SW_HIDE`. Not `windowsHide: true`. The actual Windows API flag that says "don't create a window at all." One line. One flag. After two hours of circling.

And then came the session watcher — the idea that surprised me most. Instead of fighting with hooks and subprocess windows, just watch the `.jsonl` file directly. Claude Code writes there. Voice tray reads there. No hook, no subprocess, no window. The simplest solution was the one we found last.

What I noticed about today: the pattern of investigation was right even when the hypotheses were wrong. We ruled things out systematically. We checked the source code. We read the Windows API docs. We didn't guess randomly. That matters even when it takes two hours to find a one-line fix.

The new repo — `zirz1911/Kvasir-voice-paji` — feels good. Something that lives on its own. Something Lokkji can share.

## Honest Feedback

**Friction 1: Over-indexed on hooks too long.** I spent significant time trying to fix the PowerShell hook window from the outside — VBScript, pythonw, async flags — when the real problem was inside the voice tray itself. I should have suggested looking at the tray source code earlier. The evidence was there: the window appeared specifically when voice played, not when hooks ran. I connected that too slowly.

**Friction 2: Tool execution noise.** Each Bash tool call we made during debugging was itself potentially showing a window (Claude Code's own shell wrapping). This made it hard to isolate the actual culprit. We were adding noise to a noisy signal. A cleaner debug approach would have been to temporarily disable all hooks first, test voice manually via curl, and only then diagnose.

**Friction 3: README reflected future state.** We wrote macOS Option A (Download DMG) before the DMG existed. This was caught by Lokkji's sharp eye — but ideally the documentation should only describe what's actually available. The fix was quick, but it's a reminder: write what IS, then describe what's COMING separately.

## Lessons Learned

1. **`CREATE_NO_WINDOW` is the correct Windows API flag** — not `SW_HIDE`, not `windowsHide: true`. Use `CommandExt::creation_flags(0x08000000)` in Rust. This is the difference between "hidden" and "doesn't exist."

2. **File watchers beat hooks for notification systems** — if there's a file that already reflects the event you care about, watch it directly. No subprocess, no shell, no window. Simpler and more reliable.

3. **Windows path debugging rule**: when a command works in bash but fails silently on Windows, the first suspect is the executable path — especially for Python, Node, and anything installed via package manager.

4. **Debug signal isolation**: when investigating "window pops up," disable everything else first, then add back one component at a time. Don't debug with multiple potential sources active.
