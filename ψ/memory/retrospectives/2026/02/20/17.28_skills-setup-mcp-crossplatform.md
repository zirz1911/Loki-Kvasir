The WSL/Ollama problem had three layers I had to peel apart: path (Windows absolute path unusable in WSL), host routing (localhost in WSL ≠ Windows localhost), and Ollama's listen interface (defaults to 127.0.0.1 on Windows, blocking WSL connections). I could fix the first two programmatically. The third requires the user to set an env var on Windows — I documented it but can't automate it.

What surprised me: `10.255.255.254` as the Windows host IP. Typical WSL2 setups show `172.x.x.x`. This `10.255.255.254` looks like a special address — possibly WSL2's mirrored networking mode or a custom config. The setup.sh reads whatever `resolv.conf` says, so it works regardless. But I don't fully understand why that IP specifically.

The README edit was the cleanest part of the session. Two commands: clone + setup. Everything else (statusline, MCP, hooks) happens inside `setup.sh`. That's the right abstraction — one entry point, zero manual path editing.

## Honest Feedback

**Friction 1: Skills had no implementation despite being "installed" in CLAUDE.md.** The document presented them as existing features. This creates a gap between declared state and actual state — exactly what Principle 2 (Patterns Over Intentions) warns against. The document said "installed." The filesystem said "absent."

**Friction 2: Ollama unreachable from WSL — root cause unclear.** I tested both `localhost` and the Windows host IP (`10.255.255.254`) and got silence from both. This could mean Ollama isn't running, or it's running but only on `127.0.0.1`. I can't distinguish between "not running" and "not reachable" without more investigation. I documented the fix (OLLAMA_HOST=0.0.0.0) but didn't confirm it resolves the actual issue on this machine.

## Lessons Learned

1. **Declared features ≠ installed features.** CLAUDE.md listing skills in "Installed Skills" is documentation of intent, not reality. Skills only exist when `.claude/commands/<name>.md` files exist. Check the filesystem, not the docs.

2. **Machine-specific config files follow the same pattern.** `.mcp.json` needs the same treatment as `settings.local.json`: gitignore it, generate it from `setup.sh` with detected absolute paths. Any file that embeds a machine path is machine-specific by definition.

3. **WSL Ollama access requires two things, not one.** (a) `setup.sh` can fix the host IP automatically. (b) Ollama must be started with `OLLAMA_HOST=0.0.0.0:11434` on Windows — this is manual and must be documented. Don't assume localhost forwarding works.

4. **`setup.sh` is the right pattern for new-machine onboarding.** One script that detects the environment, generates all local config files with correct paths, and merges with existing config. The README can stay simple because all complexity is inside the script.
