## Honest Feedback

**Friction 1**: Dashboard grep patterns are too fragile — they miss if health output isn't in the captured pane at the right moment. The 35s sleep is a guess, not a guarantee. For 3 instances this is acceptable but it will give false readings regularly.

**Friction 2**: Sending shell commands to a pane running Claude Code requires routing through Claude Code (asking it to "run bash: X") — not obvious until it fails. The mental model needs to be: "is this pane in shell mode or Claude Code mode?" before sending.

---

## Lessons Learned

1. **Dashboard timing is probabilistic, not deterministic.** `sleep 35` after sending health commands is a best-effort wait. If health check takes longer (gateway wake-up, slow network), the captured output will miss it. Design dashboards to either wait for specific output patterns or accept that readings may be stale.

2. **SSH idle timeouts are normal for remote sessions.** claude29 and claude30 drop regularly when idle. Build fleet management workflows around the assumption that sessions will need reconnecting — not around the assumption they stay alive.

3. **Check what mode a tmux pane is in before sending.** A pane running Claude Code interactively will treat anything you type as a chat message. A bare shell pane will execute it. The mode determines how to route commands. Always capture-pane first to check if needed.

4. **`openclaw health` gateway errors after reconnect indicate token mismatch in config.** Fix: ensure `gateway.remote.token` in `~/.openclaw/openclaw.json` matches `gateway.auth.token`. This is a config issue, not a gateway crash.
