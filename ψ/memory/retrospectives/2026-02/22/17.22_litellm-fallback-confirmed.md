fallback config อยู่ใน YAML มาตั้งแต่ session ก่อน แต่ไม่เคยทดสอบจริงๆ พอทดสอบ พบว่าไม่ work เลย เพราะสองเหตุผลที่ไม่ได้คาดไว้:

เหตุผลแรก: proxy ที่กำลัง run อยู่ load config ตอน startup เท่านั้น ถ้า config เปลี่ยนหลังจาก proxy start แล้ว config ใหม่จะไม่มีผล ต้อง restart proxy — สิ่งนี้ฟังดูชัดเจนมากเมื่อคิดย้อนหลัง แต่ตอนนั้นไม่ได้คิดถึงเลย

เหตุผลที่สอง: fallback ใช้ real Anthropic API แต่ ANTHROPIC_API_KEY ไม่ได้ถูก set ใน environment ของ proxy process เพราะ start-litellm.ps1 ไม่ได้ include มัน การแก้ง่ายมาก แค่อ่านจาก api_key file

เรื่อง Ollama tray app ก็ surprise ดี — คิดว่า kill process เดียวพอ แต่มี watchdog อยู่ใน background ที่คอย restart ตลอด pattern นี้คล้ายกับ systemd service บน Linux ที่ถ้าจะหยุดต้องใช้ `systemctl stop` ไม่ใช่ `kill pid`

สิ่งที่พอใจที่สุดวันนี้คือ pipeline ครบวงจรทำงานได้จริงแล้ว: Ollama up → local model ฟรี → Ollama down → real Claude auto อ่านต่อ ผู้ใช้ไม่ต้องทำอะไร มัน transparent ทั้งหมด

## Honest Feedback

**1. "ตั้งค่าแล้ว" ≠ "ทดสอบแล้ว"** — ในทั้ง session นี้และก่อนหน้า มีหลายอย่างที่ตั้งค่าไว้แต่ไม่ได้ test จนถึง session นี้ (fallback, MCP tools) สำหรับ infrastructure ควร test ทันทีหลัง setup ไม่ใช่ session ถัดไป

**2. Process management บน Windows ซับซ้อนเกินจำเป็น** — ต้องเขียน .ps1 script แยก kill-ollama.ps1 เพราะ bash-on-Windows ไม่จัดการ Windows process names ได้ตรงๆ ถ้า dev environment เป็น Linux/Mac คงใช้ `pkill ollama` จบเลย

**3. LiteLLM proxy เป็น stateful process ที่ต้อง restart ทุกครั้ง config เปลี่ยน** — ไม่มี hot-reload ถ้าต้องการแก้ config บ่อย (เช่นเปลี่ยน model) ต้องมี workflow ที่ชัดเจน: แก้ yaml → kill proxy → start ใหม่ ควร script สิ่งนี้ไว้ใน reload-litellm.ps1

## Lessons Learned

1. **Restart proxy หลังแก้ config เสมอ** — LiteLLM load config ครั้งเดียวตอน start ไม่มี hot-reload
2. **Ollama tray app คือ watchdog** — ต้อง kill ทั้ง `ollama` + `ollama app` พร้อมกัน ถ้า kill แค่ server จะ restart ทันที
3. **ANTHROPIC_API_KEY ต้องอยู่ใน env ของ proxy process** — ไม่ใช่แค่ใน config file — ต้อง set ก่อน launch
