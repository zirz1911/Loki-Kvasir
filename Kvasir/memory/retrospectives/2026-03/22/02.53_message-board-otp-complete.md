## AI Diary

This session had a satisfying rhythm — every few exchanges revealed the next layer of the system. The card config work was the most important structural decision: instead of hardcoding `profile_id` everywhere, we built a `CARDS` map keyed by phone number. Now every webhook call — setup or OTP — derives its credentials from the active card. That's the kind of change that prevents a whole class of bugs.

The iOS phone number highlight issue was a good reminder that mobile browsers are aggressive about "helpful" behaviors. `format-detection` is the right tool, but even after disabling it, we added `pointer-events: none` on the number text as a belt-and-suspenders fix. Worth knowing.

The `handleMessageEvent` function was the most interesting logic this session. The insight: when an OTP arrives, the countdown is no longer meaningful — the job is done. And when `No SMS` arrives, it's a specific failure mode that needs a specific action. So instead of one generic "message received" handler, we branch on content. Clean and honest.

The credential swap-and-revert was a small moment but instructive. The user changed `device_id` and `workflow_id`, then asked to revert. Because we had moved everything into named constants at the top of the script, the revert was two lines. That's the payoff for centralizing config: changes and reversions are trivial.

One thing I keep noticing: the server restart pattern is genuinely annoying. `pkill` exits 144 when nothing is running, which breaks the `&&` chain, so the server never starts. The workaround is always a second background job. Should really just write a proper `restart.sh` or switch to `nodemon`.

## Honest Feedback

**1. Server restart is still broken.** The `pkill -f "node server.js" && node server.js` pattern fails because pkill exits non-zero when no process is found. This has happened every single session. It's a known issue that keeps not getting fixed. The real solution is `nodemon` for dev or a small `restart.sh` that doesn't depend on pkill exit code: `pkill -f "node server.js"; sleep 1; node server.js &`.

**2. The `CARDS` config is still in the HTML file.** This is fine for now, but it means every time a number or profile_id changes, you edit a 1000-line HTML file. As the number of SIM cards grows, this will become painful. A separate `cards.json` read by the server and served via a `/cards` endpoint would separate concerns cleanly.

**3. No way to confirm webhook success in the UI during setup.** The setup screen fires the webhook and then waits for `SETUP DONE` via SSE. But if the webhook itself fails (network error, GemLogin rejects it), the spinner just hangs forever. There's no timeout, no error state, no feedback. The user would have to manually navigate back. An error state after 3-5 minutes of no response would improve resilience significantly.

## Lessons Learned

- Centralizing credentials (`TOKEN`, `DEVICE_ID`, `WF_OTP`, `WF_SWAP`) as top-level constants makes swaps and reversions trivial — do this from the start
- iOS/Android auto-detects phone numbers and styles them as links — use `<meta name="format-detection" content="telephone=no">` + `pointer-events: none` on number elements
- Branch on message content for state transitions (OTP vs No SMS) — specific failure modes need specific actions, not a generic handler
