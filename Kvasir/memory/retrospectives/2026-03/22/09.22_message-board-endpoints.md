## AI Diary

This session had a satisfying arc — it started with confirming something worked (the disconnect-safe OTP long-poll), then moved into pure feature addition. The swap endpoint was the simplest: just copy the OTP endpoint pattern, swap `WF_OTP` for `WF_SWAP`, done. The pattern was already established so there was nothing to design.

The `/begin-setup` endpoint is more interesting. Its purpose shifted during the session. It started as a "trigger setup UI automatically" endpoint — automation sends a number, browser opens setup view. But then the user said "I just want to see what numbers come in" and we stripped it back. No webhook, no navigation, just log and broadcast. That's a much cleaner single-responsibility design. I should have asked about the intent earlier instead of assuming "begin-setup" meant "kick off the full setup flow."

The SETUP_LOG tab required the most frontend work: nav tabs with active state management, a new view, table rendering, real-time SSE updates, and initial history load from the server. The tricky part was making `showOnly()` aware of the nav tabs — they should only be visible in list/log views, not in setup or detail views. Adding `navTabs.style.display` to `showOnly()` was the clean solution.

The "accept any number" change at the end was the right call. The user's workflow involves numbers not yet in the CARDS config — they add numbers to their device first, then the automation starts using them. A server that rejects unknown numbers would be a constant friction point. Removing the validation makes the endpoint genuinely useful as an automation receiver.

## Honest Feedback

**1. I assumed "begin-setup" meant "auto-navigate to setup view."** The name suggests it, but the user's actual need was just logging. I built the auto-navigation, it got removed a few messages later. Should have asked "do you want the UI to navigate automatically, or just record it?" before building the full behavior. The extra code was trivial to remove but it cost a clarification round.

**2. The CARDS config is still duplicated between server.js and index.html.** Both files have identical `CARDS` objects. Every time a new number is added, it needs to be updated in two places. This was noted in the last retrospective too — it keeps not getting fixed. A `/cards` endpoint served from server and consumed by frontend would solve it permanently.

**3. No persistence for setupLog.** The log lives in memory — a server restart wipes it. For a monitoring tool where you want to track which numbers came in across a work session, losing history on restart is annoying. Even appending to a `.log` file on disk would be better than pure memory.

## Lessons Learned

- Ask about intent before building UI behavior — "trigger X" and "record X" are different requirements that lead to very different implementations
- `showOnly()` is the right centralization point for view-dependent chrome (like nav tabs) — one place to control what's visible
- Removing validation at system entry points (when the system genuinely should accept unknown input) is a feature, not a compromise
