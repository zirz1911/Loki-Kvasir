## Honest Feedback

**Friction point 1: Background script as embedded string**
The core design problem here is that `_refresh_usage_bg()` embeds a Python script as a string inside the main script. This creates a maintenance nightmare where any fix to the outer script doesn't automatically propagate to the inner script. The Keychain fix from March 1 improved `_get_token()` in the main code but left the background string untouched. A better architecture would be to extract the background logic into a separate helper script file that can be versioned, tested, and maintained independently. The embedded string approach feels pragmatic but accumulates drift over time.

**Friction point 2: Silent failure with no diagnostics**
When the background script fails, it swallows the exception silently (`except Exception: pass`). This is intentional — we don't want the statusline to crash because usage fetch failed — but it means debugging requires manually running the embedded script code in isolation. There's no error log, no timestamp of last failure, nothing. A minimal improvement would be writing a failure marker to a temp file so that the main code can at least show "usage: ?" with a different color indicating "refresh failed" vs "no data yet."

**Friction point 3: Duplication of credential logic**
The credential retrieval logic now exists in two places: the main `_get_token()` function and the embedded background script's `_get_token()` inner function. Any future change (new Keychain service name, new credential format) must be applied in both places manually. This is the same problem as friction point 1 viewed from a different angle — the embedded string pattern forces logic duplication.

## Lessons Learned

1. **Embedded subprocess scripts drift from their host** — when a fix is applied to outer code, always check if the same logic is duplicated in any embedded script strings
2. **Python 3.14 on macOS has no root CAs** — use `certifi` for any HTTPS calls; `ssl.create_default_context()` alone will fail
3. **Silent background failures need breadcrumbs** — even a temp file with last error timestamp would make future debugging much faster
