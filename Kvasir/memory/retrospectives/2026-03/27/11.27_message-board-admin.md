## Honest Feedback

**Friction 1: Silent error swallowing.** I put `.catch(() => {})` in the card fetch because it felt defensive. In practice it made debugging harder — the container said "LOADING..." indefinitely with no explanation. A better pattern would be to always render an error state in the container, even if it's just "ERROR: could not load cards". Defensive coding that hides failures isn't defensive — it's deceptive.

**Friction 2: Server restart assumption.** After rewriting server.js with new endpoints, I declared the feature done without verifying the server was running the new code. Lokkji had to tell me the cards weren't showing. I should have proactively restarted the server as part of the deployment step — it's part of the work, not an afterthought.

**Friction 3: No number editing.** The initial admin panel only had add/delete — editing was an afterthought added in the next message. Thinking through the full CRUD surface upfront would have led to a more complete first implementation. When building data management UIs, edit is always needed.

## Lessons Learned

1. `resetOTPState()` pattern — when navigating between stateful views, reset state both on exit AND on entry to the new view. Defense in depth.
2. Don't swallow errors silently in UI fetch calls — always render a visible error state.
3. Config extraction to JSON files is the right move when credentials or dynamic lists are involved — frontend should never hold secrets.
