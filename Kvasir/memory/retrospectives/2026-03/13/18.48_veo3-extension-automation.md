## AI Diary

This session was a perfect example of what I love and hate about web automation. The target changed completely — Google Labs Flow had a new UI with new XPaths, new event models, and new DOM patterns. We started confident: three clear XPaths, simple enough. Then reality hit.

The file upload fight was genuinely humbling. We tried: direct inject (worked but no navigation), button click (opened native file picker), drag-and-drop events (nothing), MutationObserver (too late), prototype override (still opened), instance override (still opened). Each attempt felt like "this is it" — and each time the OS file dialog mocked us. The final solution was elegant in hindsight: `addEventListener('click', preventDefault, true)` in the capture phase. The browser's native behavior for `input[type="file"]` responds to the raw click event before JavaScript normally intercepts it, so capture phase is the only reliable interception point.

The Slate editor was another layer. `textarea.value = text` is a fond memory. Slate uses a virtual editor model — it listens to `beforeinput` events, not DOM mutations. Once you know this, it's clean. But discovering it requires knowing to look.

The dropdown pattern (Radix UI + human-like MouseEvent sequence) was the final piece. `.click()` doesn't trigger Radix dropdowns because Radix uses pointer event listeners, not click handlers. `humanClick()` — the pointerdown→mousedown→pointerup→mouseup→click sequence — is now a core utility in this extension.

What made this session work was Lokkji's methodical feedback loop. Every failed attempt came with logs and HTML elements. No guessing. Each iteration was informed. That's the trickster's preferred environment: real signals, fast feedback, no assumptions.

## Honest Feedback

**Friction 1 — Too many approaches for one problem**: The file upload took 7+ commits and 6 different strategies. In hindsight, `capture-phase preventDefault` should have been attempted much earlier. The DOM manipulation approaches (files setter, drag-drop, prototype override) were all working around the wrong layer — the OS dialog is triggered by the browser's native input activation, not by JavaScript. Understanding that distinction earlier would have saved 4-5 rounds.

**Friction 2 — Class-based selectors are fragile**: Several times we used CSS classes like `sc-46973129-1`, `sc-a0dcecfb-1`, `sc-dbfb6b4a-0` from styled-components. These are generated hashes that can change with any build. Lokkji had to provide actual DOM elements multiple times to confirm the correct selectors. Better approach: always prefer semantic attributes (`aria-haspopup`, `role`, `data-*`) or text content over generated class names.

**Friction 3 — Dropdown not opening with `.click()`**: Lost time because Radix UI uses pointer events, not click events for state changes. Should have immediately tried `humanClick()` (MouseEvent sequence) when the first `.click()` attempt failed silently. The pattern is well-known in automation contexts.

## Lessons Learned

1. **`capture-phase preventDefault` blocks native file input activation** — override at `document.addEventListener('click', handler, true)` with `e.preventDefault()` when `e.target.type === 'file'`
2. **Slate editors use `beforeinput` events** — insert text via `InputEvent('beforeinput', { inputType: 'insertText', data: text })`
3. **Radix UI requires pointer event sequence** — `.click()` alone doesn't open Radix dropdowns; need pointerdown→mousedown→pointerup→mouseup→click
4. **MutationObserver timing** — if target element already exists in DOM, observer won't fire; always block pre-existing elements AND new ones
5. **Detect upload completion by img src change** — more reliable than counting DOM elements (which may be virtualized/paginated)
