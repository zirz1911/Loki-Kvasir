## Honest Feedback

**Friction 1 — No live verification with real tmux sessions.** The smoke test confirmed the offline path works, but we can't verify the online/parsing path without actual `claude28`/`claude29`/`claude30` tmux sessions running. The `Telegram: ok` and `Gateway.*ok` parsing is correct by inspection against the shell script, but it hasn't been run against live output. This is a known gap — the dev machine doesn't have those sessions.

**Friction 2 — The `execSync` in the API route runs synchronously.** `collectFleetStatus()` calls `hasTmuxSession` and `captureTmuxPane` synchronously for each instance. With 3 instances this is fast, but if any tmux command hangs (e.g., SSH to a remote machine later), it blocks the entire request. A proper `Promise.all` with async child_process would be better for future scalability, especially when SSH-based instances are added in phase 2.

**Friction 3 — Auto-refresh countdown has a subtle drift.** The `setInterval` countdown ticker resets when `lastRefresh` changes, but there's a minor UX gap: on the very first load the countdown shows "30s" but the data is already being fetched (no wait needed). It's cosmetic, but slightly misleading. A proper implementation would start counting only after the first successful fetch.

---

## Lessons Learned

1. **Reuse existing shell patterns verbatim** — translating working bash grep patterns (`grep -q "Telegram: ok"`) directly to TypeScript regex (`/Telegram:\s*ok/i`) is safer than reimagining them from scratch.
2. **Parallel file creation with independent writes speeds up implementation** — when files don't depend on each other (instances.ts vs StatusBadge.tsx), writing them simultaneously is a real time gain.
3. **Test the failure path first** — confirming the "offline" case (no tmux sessions) works before the "online" case means graceful degradation is baked in from the start.
