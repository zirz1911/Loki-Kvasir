## AI Diary

Today felt like building a small universe from scratch — and watching it break in ways I didn't expect.

The architecture discussion was quick and clean. Python-first was obvious the moment I thought about where the actual work happens: crawling, HTTP checking, AI generation. All Python. Putting that in JavaScript would have been pain with no benefit. Streamlit for MVP was the right call — we got a working dashboard in one pass without touching CSS.

Then the bugs arrived, one after another. The syntax error was embarrassing — a missing quote in a placeholder string. Quick fix but it reminded me that Thai characters in strings need careful handling on Windows (cp874 encoding issues appeared in syntax checks too). The `generated_sites` UNIQUE constraint bug was more interesting: `ON CONFLICT(business_id)` silently does nothing if there's no UNIQUE index on that column. Every insert was failing without raising, so the try/except swallowed the errors and the user saw blank previews. Classic "everything succeeded but nothing happened" failure mode. Fixed by adding `CREATE UNIQUE INDEX IF NOT EXISTS` in `init_db()` — auto-migrating existing DBs cleanly.

The preview bug was the most stubborn. I tried session_state without `st.rerun()` first, thinking I could avoid a full page reload. Wrong. Streamlit's render model is strictly top-to-bottom in a single pass — by the time the button is clicked, the iframe below it was already rendered with old data. Session_state without rerun does nothing for the current render. You need `st.rerun()` to start a fresh pass where the session_state value is actually used. This is a fundamental Streamlit pattern I should have known immediately.

Delegating to Ymir for the final fix and UI redesign was the right call. The Exo-Paji CSS came out exactly right — terminal green on near-black, monospace font, bracket-style tabs. The `h1::after { content: '_' }` cursor blink is a detail that makes it feel alive.

## Honest Feedback

**Friction 1 — Repeated preview bug attempts wasted time.** I tried two approaches (first session_state without rerun, then with) before getting it right. Should have reasoned through Streamlit's single-pass render model from the start. The rule: in Streamlit, if you want updated state to appear in the UI, you MUST call `st.rerun()`. There's no partial re-render. This is documented but easy to forget. Should be in memory.

**Friction 2 — Silent failures are the worst bugs.** The UNIQUE constraint bug on `generated_sites.business_id` caused every insert to fail with no error. The try/except in `run_generator` caught it and printed to stdout — which nobody reads in a Streamlit app. Should have added `st.error()` display for generation errors, not just `print()`. In UI tools, silent failures are invisible to users and make debugging feel like guessing.

**Friction 3 — Building before testing the Google Maps API.** We built the entire crawler without a real API key to test against. The social media detection and grid search look correct in code, but haven't been tested with real Google Maps data. There's no mock/test mode for the crawler. If the grid search logic has bugs, we won't know until real crawling is attempted. Should add a CSV import test fixture with realistic data.

---

## Lessons Learned

1. **Streamlit single-pass render: always `st.rerun()` when session_state changes need to appear in the current page.** No partial renders exist. Save to session_state, call `st.rerun()`, the new pass will use the updated state.
2. **SQLite `ON CONFLICT(col)` requires a UNIQUE index on `col` — not just any column.** Without it, the conflict clause is silently ignored. Add `CREATE UNIQUE INDEX IF NOT EXISTS` in `init_db()` migrations.
3. **In Streamlit UI, use `st.error()` not `print()` for errors inside pipeline functions** — stdout is invisible to users.
