## AI Diary

There's something almost meditative about this kind of work — iterating on browser automation that you can't directly see, where the only feedback is "it didn't work" and the only tool is logic. Each time the user reported a failure — "ไม่เห็นกด + เลย", "เปิด Extension ไม่ได้", "ต้องกดกลับก่อน" — I had to reconstruct the UI state from pure HTML snippets and reason about what state the page was in.

The double upload bug was the most interesting one. The underlying problem: each call to `clickUploadImage` ended with `waitForUploadAndSelect`, which waited for `.sc-dbfb6b4a-0` to disappear. After the first upload, the dialog *was* the thing holding the upload button — so it disappearing meant the second upload had nowhere to go. The fix was architectural: don't try to be clever about it, just re-click `+` to reopen a fresh dialog for the second image.

The `humanClick` vs `robustClick` discovery was also valuable. For React components that intercept events through fiber, `humanClick` (raw MouseEvent dispatch) often misses. `robustClick` walks up the React fiber tree and fires the `onClick` handler directly — much more reliable for buttons that don't respond to DOM events alone.

The video gen pipeline rewrite felt clean. The old code had a `clickStart()` step looking for a "เริ่ม/Start" div that no longer existed. Replacing it with the actual UI flow — settings button → VIDEO tab → escape to close — maps exactly to what a human does. Every time I can make the automation mirror human behavior exactly, it gets more stable.

The "เปิด Extension ไม่ได้" errors were frustrating because the files were syntactically valid. Those are probably Chrome's service worker reload issues or CSP violations — hard to diagnose without the actual error message. The user eventually got it working both times without sharing the error, which suggests it may have been a timing/reload issue rather than a code bug.

## Honest Feedback

**1. Error messages matter more than file checks.** Both times the extension failed to open, I checked syntax and file existence — both came back clean — and had to tell the user to share the error message. The user never did. This wastes a full round-trip. I should have immediately asked for the error screenshot before doing any investigation, because `node --check` and `JSON.parse` can't catch Chrome-specific issues (CSP, service worker scope, missing permissions).

**2. The UI automation is brittle by design.** Every step relies on class names (`sc-46973129-1`, `sc-dbfb6b4a-0`) that are hashed by CSS-in-JS and will change on any rebuild of the Flow app. The XPath selectors using icon text (`normalize-space(text())="add_2"`) are more stable, but the mix creates an inconsistent baseline. At some point this will break silently mid-session and be hard to diagnose.

**3. I'm adding steps reactively.** Back button, clear prompt button — each of these was discovered when the automation ran and the user noticed it was missing. There's no way to know the full UI flow without running it or having the user describe every click. A short "describe every click you make manually" session upfront would save 3-4 fix cycles.

## Lessons Learned

- Re-click the trigger button (like `+`) to reopen dialogs when flow requires multiple uploads into separate dialog sessions
- `robustClick` > `humanClick` for React fiber components — always prefer it for uncertain cases
- Store intermediate artifacts (generated images) in `chrome.storage.local` as the bridge between pipeline stages
- UI automation needs the full manual click sequence described upfront — every modal, every clear, every back button
