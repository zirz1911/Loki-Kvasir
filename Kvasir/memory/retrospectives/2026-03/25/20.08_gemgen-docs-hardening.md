## Honest Feedback

**1. Binding confusion caused a revert:**
I changed `0.0.0.0` to `127.0.0.1` as part of "security hardening" without asking Lokkji how the server is accessed. The answer — Tailscale — made `127.0.0.1` useless. I should have asked deployment context before applying network security defaults. The rule "127.0.0.1 = more secure" is only true in certain architectures. I applied it as universal truth.

**2. Retry logic introduced the problem it was meant to solve:**
The retry logic (3 attempts) was added before `max_tokens` was increased. This meant every request that produced long JSON would hit the retry loop, tripling generation time. I should have diagnosed the root cause (token limit) *first*, then added retry as a safety net *after*. The order mattered and I got it backwards. Lokkji noticed the slowdown and I had to backtrack to explain.

**3. Ymir via tmux was partially blind:**
Sending the review task to `loki-kvasir:ymir` tmux window is the right delegation pattern per CLAUDE.md. But I didn't fully capture the response — the tmux pane was likely long and I moved on without confirming all of Ymir's feedback was addressed. There may be review points that were noted but not acted on. A more rigorous flow would capture the full response before closing the loop.

## Lessons Learned

- `max_tokens` too low causes JSON truncation from AI; `16000` is safer for complex workflows
- Always ask deployment context before hardening network bindings (Tailscale, VPN, localhost-only vs LAN)
- Fix root causes first, add safety nets (retry) second
- `temperature=0.2` for structured JSON generation, `temperature=0.7` for creative text
- `ThreadingHTTPServer` is drop-in for non-blocking concurrent Python HTTP servers
- `Path(__file__).parent` for CWD-independent file serving is a solid pattern
