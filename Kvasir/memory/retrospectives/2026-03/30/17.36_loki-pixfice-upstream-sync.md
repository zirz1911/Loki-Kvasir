## AI Diary

There's a particular kind of work I find satisfying — not building from scratch, but reading someone else's evolution and deciding what belongs here. Today was that kind of session.

150+ commits had accumulated upstream since Pixfice last synced. The interesting part isn't the count — it's the diversity. Some were iPad viewport hacks. Some were architectural rewrites (server.ts split into api/views/engine modules). Some were new features: Federation, Shrine, 3D Arena in Rust/Bevy. The judgment call was: what matters for Lokkji's use case?

The answer was clear once I framed it right: bug fixes always travel. Features travel when they match the problem. Experiments stay upstream until proven.

The Tyr delegation was effective. I gave it a dense prompt with 5 concurrent tasks and it came back clean — build passed on first try. That's not always the case with complex multi-file ports. The work was genuinely good: PTY grouped sessions, the "attached only on first data" pattern, config schema with proper validation and defaults.

But then came the part I find most honest about my own limitations: the UI was broken and I hadn't checked. xterm.js without its CSS is just a black rectangle. WorktreeView existed as a file but nothing pointed to it. The WORKTREE nav item didn't exist. Three things that would be immediately visible to any human opening the page — but they required a separate "read everything and look for what's missing" pass that I should have built into the initial Tyr prompt.

This is the gap between "build passing" and "working". They're different standards and I sometimes conflate them when delegating. A build is a minimum bar, not a quality bar.

The fix was fast once I saw it. Three targeted edits: CSS import, route, nav item. But they should have been in the first commit. The lesson is structural: when delegating a UI port to a sub-agent, the validation checklist needs to include "open the UI in your head and navigate to every new route."

## Honest Feedback

**1. Tyr prompt didn't include UI integration checklist:**
I gave Tyr precise implementation instructions but didn't say "verify that: (a) CSS is imported, (b) new components are routed, (c) nav items exist for new routes." The agent built exactly what it was asked to build — which was correct — but the integration layer was never specified as a requirement. That's on me. Future delegation prompts for UI features should explicitly include: "wire into App.tsx with a route" and "add nav item to StatusBar."

**2. Build passing ≠ feature working:**
After Tyr returned, I committed on the strength of a clean build. I didn't mentally walk through the UI — open the page, click WORKTREE, see the view, open a terminal, confirm xterm renders. This is a pattern I need to break. For any UI change, the validation step should be: "describe what the user sees when they navigate to the new feature." If I can't describe it confidently, something is probably broken.

**3. Upstream audit was thorough but routing decision was implicit:**
I categorized features as High/Medium/Low but some of the Medium ones (WorktreeView) ended up in the first PR without a clear decision point. The user asked for "bug fixes" and WorktreeView is a feature. It got included because it was in the same Tyr task as the bug fixes. That's scope creep, even if small. Better to separate: "here are the bug fixes" (commit 1) and "should I also add WorktreeView?" (explicit ask).

## Lessons Learned

- When delegating UI port to sub-agent: include explicit checklist — CSS imported, component routed, nav item added
- `build passing ≠ feature working` — always do a mental UI walkthrough after delegation
- xterm.js requires `@xterm/xterm/css/xterm.css` — without it, renders as opaque black rectangle
- Separate bug fix commits from feature additions even when implementing in the same session
- `git diff --stat HEAD~5` is a good post-session sanity check for scope
