## AI Diary

Today was a session where I felt the difference between "technically responsive" and "actually usable on a phone." The viewport had `initial-scale=1.0` which sounds right — but iOS Safari has its own ideas. When the user taps an input with font-size under 16px, it zooms in. Not because the viewport is wrong. Because Apple decided your form element is too small to read and helpfully zooms you in. The fix exists (`user-scalable=no`, `maximum-scale=1.0`), and I knew it — but the first pass only added `maximum-scale=1.0`, which isn't enough. iOS still zoomed. The user came back: "ยังซูมเข้าเองอยู่." That one-line message carried the full weight of "you didn't finish the job." I added `user-scalable=no` and it stopped.

The MobileBottomNav removal was the most satisfying change. It was taking 62px of vertical space on a small screen, it was a separate component with its own hash listener, and it had hardcoded active route logic that was already stale. Replacing it with a dropdown in the CEOBar navbar simplified the code and gave back screen real estate. One less thing fighting for space.

The Chat panel fix was architectural. The original mobile overlay was `position: fixed; inset: 0` — which means it covered everything including the navbar you just pressed to open it. The fix: don't use fixed positioning. Render the chat as a sibling to the CEOBar inside the column, so it naturally flows below the header. Simple. But required understanding the full layout structure to see it clearly.

What I'm still noticing: the Terminal page UI is pure vanilla HTML/CSS/JS while the Office is React. Maintaining two separate nav systems, two hamburger implementations, two viewport fixes — it's becoming harder to keep in sync. But refactoring the terminal into React would be a big task, and it works. So we keep it parallel for now.

## Honest Feedback

**1. Two-codebase maintenance is friction.** The Terminal page (`ui.html`) and the React Office app have completely separate implementations of the same patterns — navbar, hamburger menu, responsive breakpoints, even the same pixel art style. Every time I improve one, I have to manually replicate it in the other. This session I had to implement the hamburger dropdown twice: once in StatusBar.tsx and once in ui.html with vanilla JS. The risk of divergence is real.

**2. iOS viewport behavior is underspecified.** `maximum-scale=1.0` sounds like it should prevent zoom. Apple's implementation doesn't honor it in all cases — input focus can still trigger zoom. The full incantation is `maximum-scale=1.0, user-scalable=no` and even that's version-dependent. This is hard to test without a physical iOS device, so the first fix failed silently. Better mobile testing setup would help.

**3. Build + restart cycle adds friction.** Every frontend change requires `bun run build:office` + server restart + manual browser refresh. This is ~30 seconds per iteration. For rapid mobile UI iteration, that's slow. A dev server with HMR (`bun run dev`) would be much faster. The project has it configured — we just always build for production, probably because the server hosts everything on one port.

## Lessons Learned

1. **iOS viewport zoom requires both `maximum-scale=1.0` AND `user-scalable=no`** — one is not sufficient. Apply to all pages in the same app.
2. **Mobile overlay positioning**: `position: fixed; inset: 0` covers the entire viewport including navbar. Use absolute positioning within a relative container instead to respect the layout hierarchy.
3. **Input zoom prevention**: Any input on mobile with `font-size < 16px` will trigger iOS auto-zoom even with viewport restrictions. Set to 16px on mobile as a baseline.
