## AI Diary

There's a particular satisfaction in sessions like this — not because things went smoothly, but because the bugs were *real*. Not typos, not missing semicolons. Real distributed-systems-style race conditions in a Chrome extension.

The `sidepanelHandlingUpload` flag was the most elegant mistake. The logic was sound: "set a flag so background.js skips the upload when sidepanel is handling it." But the flag was set in the `videoReady` handler — which fires at the *same time* as background.js's own `videoReady` listener. Both listeners wake up from the same event. Background.js does `await chrome.storage.local.get(...)`. Sidepanel does `chrome.storage.local.set(...)`. Chrome's storage writes are async. The get resolves before the set commits. Flag is false. Background.js proceeds. Race lost.

The fix was embarrassingly simple once seen: set the flag at button-click time, before any async work begins. The flag is in storage long before `videoReady` ever fires. No race.

The FFmpeg CSP issue was a different beast — a third-party library creating blob URLs internally, which Chrome MV3 categorically blocks. Patching the minified file directly felt surgical and slightly dirty, but it was the right call. The `f()` function was creating blob URLs only to hand them back as worker paths. Replacing it with `Promise.resolve(t)` — return the original URL — was a one-line fix that eliminated the entire problem.

The cancel button situation revealed something interesting about UX assumptions. The overlay blocks the user's view of the sidepanel cancel button. The user is staring at the Flow page. The cancel they need is *there*, not hidden behind a dark panel they can't interact with. The fix was to put the cancel where the user's eyes are.

## Honest Feedback

**1. Async flag patterns are fragile.** Setting state in response to an event, when multiple listeners may race for the same event, is a recurring source of bugs. The `sidepanelHandlingUpload` pattern needed to be set *before* the event is possible, not *in response to* the event. This principle will apply again. Worth encoding as a team rule: "flags that gate concurrent behavior must be set before the operation starts, never during."

**2. Minified third-party files as source of truth is uncomfortable.** Patching `ffmpeg.min.js` works, but it's brittle. Any FFmpeg.wasm update would overwrite the patch. Should document this prominently or find a way to intercept the blob URL at a higher level (e.g., monkey-patching `URL.createObjectURL` in the extension context). Not urgent but worth noting.

**3. Error propagation in Chrome message passing is confusing.** The pattern `chrome.runtime.lastError ? { error } : res` conflates "connection failed" with "content script returned an error object." This caused `sendToTikTok` to re-inject the content script when the real error was "Upload button not found." The new code is cleaner but the lesson is: always check what kind of error you're handling before deciding what to do with it.

## Lessons Learned

- Race condition pattern: flags that gate concurrent async behavior must be set *before* the triggering event, not in response to it
- Chrome MV3 blocks `blob:` in `script-src` — FFmpeg.wasm needs direct extension URLs, not blob URLs
- `chrome.runtime.lastError` ≠ content script `{ error: ... }` response — need to distinguish before deciding to retry/reinject
