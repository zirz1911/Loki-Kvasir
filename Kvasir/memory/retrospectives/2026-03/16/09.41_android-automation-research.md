## AI Diary

There's something fascinating about this session that I keep returning to. We started with a very concrete problem — a mobile user closing a Chrome Extension popup and losing all their form state — and ended up deep in the world of Android automation, LLM-powered device control, and workflow generation AI.

The VEO3-Extension work was satisfying in a specific way. The problem had a clear shape: popup closed = process died = state lost. The solution had three layers: background service worker as persistent relay, chrome.storage.local as persistent state store, and restore-on-open so the user sees continuity. What made it interesting was the `chrome.storage.session` trap — it sounds right (session-scoped, perfect for ephemeral state), but it requires Chrome 102+ and silently fails on older mobile Chrome. The fix was blunt: `sed -i` every `storage.session` → `storage.local`. Sometimes the right answer is boring.

The /learn sprint was different energy — more like building a map. Escrcpy taught me that Electron doesn't have to be a monolith: the plugin-based init pattern with `.use(sandboxPlugin).use(terminalModule)` is elegant. The custom `electron-ipcx` package solving the IPC callback problem (passing a function as a parameter across process boundary) — that's the kind of insight that sticks.

DroidRun showed the state of LLM-powered Android automation: a Portal APK installed on the device exposes the accessibility tree, the LLM generates CodeAct or planning steps, and the whole thing works across Claude/GPT-4/Gemini/Ollama. The macro recording mode is clever — you can record once, replay forever, and the LLM can modify the macro dynamically.

GemGen was the most minimal: a Python HTTP server, a Claude API call with 500-line system prompts, and a JSON download. No DB, no auth, no complexity. Sometimes the right architecture is almost nothing.

The meta-lesson from the ecosystem scan: we're in the "pick your abstraction level" era of Android automation. Raw ADB (Escrcpy) → LLM CodeAct (DroidRun) → workflow graphs (AutoGLM, GemGen) → visual recording (Macro mode). Each level trades control for accessibility.

## Honest Feedback

**Friction point 1 — Haiku agents can't write files in /learn**: The biggest repeated frustration this session. We spawn Haiku agents to explore repos and write docs, they return the content as text in their response instead of actually writing the files. This broke /learn for droidrun and gemgen — the content was generated twice (once in the old context window, lost; once in the new one, finally written because we switched to `thor` subagent_type). The fix is to use `thor` subagent_type for /learn agents since those have Write tool access. This needs to be documented in the /learn skill instructions as a critical known issue.

**Friction point 2 — Context window compression loses work**: The context window ran out mid-session while three /learn runs were in parallel. The summary was good but the agent content (droidrun, gemgen docs) wasn't preserved — just "agent returned content but FILES NOT WRITTEN YET". This is a fundamental limitation, but the lesson is: write files immediately when agents return content, don't let them sit in context.

**Friction point 3 — chrome.storage.session silent failure**: This burned a debugging cycle. `chrome.storage.session` fails silently on incompatible Chrome versions rather than throwing an error. The API documentation doesn't prominently warn about this. Any Chrome Extension targeting mobile should default to `chrome.storage.local` and only use `session` when the version requirement is explicitly acceptable.

## Lessons Learned

1. Use `thor` subagent_type (not `haiku` model on general-purpose) for /learn agents — thor has Write tool access
2. Chrome Extension mobile state: always `chrome.storage.local` by default; `session` requires Chrome 102+
3. Android automation stack levels: ADB → LLM CodeAct → workflow graphs → visual macros — know where you are
4. DroidRun Portal APK pattern: install on device, expose accessibility tree, LLM interacts via structured API
5. GemGen minimal pattern: one HTTP server + one Claude API call + system prompt = complete AI tool
