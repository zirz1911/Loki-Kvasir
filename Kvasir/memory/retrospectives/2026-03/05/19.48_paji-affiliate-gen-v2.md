## AI Diary

This session was a detective story wrapped in a build loop. The freeze bug haunted us across three iterations. First I suspected missing audio tracks and added anullsrc fallback — reasonable hypothesis, didn't fix it. Then I fetched the Paji-editz GitHub repo and read `core/video.py` carefully. The answer was right there: they use `-an` when trimming individual clips. Not because they don't care about audio — but because they never needed it there. Audio gets added once, at the final merge step. Our code was trying to preserve audio through every intermediate step, which introduced inconsistencies when some clips had no audio stream.

The pattern was clear after that: over-engineering causes fragility. A simple `-an` flag and some frame-rate normalization (`fps=30,format=yuv420p`) solved what three other attempts couldn't. The lesson isn't just about ffmpeg — it's about trusting minimal pipelines. Each stage should do one thing. Clip trim does video normalization. Audio merge does audio. Mixing them created coupling that broke under edge cases.

The build cycle (pyinstaller + TaskOutput polling) was smooth. Having `build.spec` already written meant rebuilds were one command. The user asked "do I need to rebuild?" after each change — which is the right instinct and shows they're thinking in deployment terms, not just development terms.

## Honest Feedback

**Friction 1 — Freeze fix took too many iterations.** We tried the audio fallback approach before reading reference code. If I had fetched Paji-editz earlier (or asked for reference earlier), we'd have solved it in one round instead of three. The lesson: when a bug persists after one fix attempt, reach for reference implementations before theorizing further.

**Friction 2 — Build loop is manual.** Every code change requires a user-initiated "build ใหม่" command. There's no watch/auto-rebuild. For a tight iteration loop this is fine, but as the codebase grows it would benefit from a `Makefile` or simple `build.bat` that users can double-click. The user asked "ต้อง build ใหม่มั้ย" three times — that friction is real.

**Friction 3 — Video quality assumptions untested.** We normalized to fps=30 and yuv420p assuming it works for all input clips. Some clips might be 60fps, some might be HDR. The `force_original_aspect_ratio=decrease + pad` approach handles resolution well, but frame rate forcing downward could cause motion artifacts in fast-moving clips. Should test with a variety of source footage.

---

## Lessons Learned

1. **ffmpeg clip pipelines should be video-only during intermediate steps** — add audio only at the final merge. This keeps each stage clean and avoids audio stream mismatch errors.
2. **Fetch reference code early** — when a bug persists after one round, look at how others solved it before hypothesizing further. Paji-editz had the answer in 5 lines.
3. **`fps=30,format=yuv420p` normalization is essential** for reliable concat demuxer operation — clips with different framerates or pixel formats cause silent failures.
