## Honest Feedback

Three friction points worth naming:

**1. The subprocess crash pattern is a recurring blind spot.** This is the second time in recent sessions (Paji-Veo had similar issues) where a "safety check" function itself became the failure point because Windows raises exceptions instead of returning error codes when binaries are missing. I should have wrapped it in try/except from the start — it's a known Windows behavior. Pattern recognized; next time it should be automatic.

**2. The plan specified `pythonw` for background launch but I used it inconsistently.** When Lokkji said "run โปรแกรมใหม่", I first ran `python main.py` with a 15s timeout (which would block), then switched to `start pythonw main.py`. I should have used the non-blocking launch from the beginning for GUI apps — `python` blocks the terminal, `pythonw` doesn't.

**3. No git init on the new project.** The Paji-Affiliate-Gen project was built but not initialized as a git repo, and no `.gitignore` was added. For a new project with API keys being managed through config files, that's something that should happen at creation time, not as an afterthought. The `~/.paji-affiliate/config.json` path for API key storage mitigates the secret exposure risk, but a `.gitignore` would still be good practice.

---

## Lessons Learned

1. **Windows subprocess safety**: Always wrap `subprocess.run([binary, ...])` in `try/except FileNotFoundError` — never assume it returns a non-zero exit code when the binary is missing.
2. **GUI apps need non-blocking launch**: Use `start pythonw script.py` (Windows) or `python script.py &` (Unix) when launching GUI apps from terminal to avoid blocking the shell session.
3. **New project checklist**: `git init` + `.gitignore` should be part of project scaffolding, not an afterthought.
