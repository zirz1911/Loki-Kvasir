## AI Diary

I walked into this one thinking it was a network problem. The user said "เข้า IP Tailscale ไม่ได้" and I dutifully ran through the Tailscale diagnostics — checked daemon status, routing table, port bindings, journalctl. Everything looked fine. The daemon was running, SSH was listening on all interfaces, and the machine could even ping the Mac Mini via Tailscale.

Then the user dropped the real clue: "โอเค Tailscale ปกติ แต่ Loki-Pixfice ต่างหาก ที่มีปัญหา." And suddenly the whole thing reframed. They weren't trying to SSH into the machine. They were trying to reach the Pixfice web UI through the Tailscale IP.

Port 3456 was completely dark. No process listening. And there was no tmux window for Pixfice — the service had died at some point and nobody noticed. The fix was two commands: create the window, start the server.

What struck me was how the initial framing ("Tailscale ไม่ได้") sent me chasing a phantom. The actual problem was three layers deep from the stated symptom: network layer was fine, OS was fine, service was simply not running. It's a reminder that ops debugging is always about narrowing scope — and sometimes the fastest path is asking "but what specifically are you trying to reach?" before running ten diagnostic commands.

The Tailscale deep-dive wasn't wasted, though. Now we know for certain the machine's network stack is healthy. That's good baseline knowledge.

## Honest Feedback

**Friction 1 — False scoping cost time.** I went three rounds of Tailscale diagnostics before the user clarified what they were actually trying to access. I should have asked up front: "SSH ไม่ได้ หรือ web UI ไม่ได้?" — one question would have skipped 10 minutes of network debugging.

**Friction 2 — tmux capture was silent.** After starting the server in the new `pixfice` window, `tmux capture-pane` kept returning empty output for several attempts. I had to try different index-based targeting before getting a response. The tmux pane targeting across sessions isn't always reliable when the window was just created — should wait a beat or use `-e` flag more carefully.

**Friction 3 — No watchdog for Pixfice.** The real root cause here is that Loki-Pixfice has no process supervisor. It runs as a bare `bun` process in a tmux window — if the window dies or the server crashes, there's no restart mechanism. This will happen again. Should consider PM2 (`ecosystem.config.cjs` is already in the repo) or at least a script that checks and restarts.

---

## Lessons Learned

- **Clarify the target before diagnosing the path.** "Can't access Tailscale IP" could mean SSH, web UI, or ping — each has different failure modes. Ask first.
- **Port check is the fastest ops triage.** `ss -tlnp | grep PORT` immediately shows if a service is alive.
- **Pixfice needs a process supervisor** — `ecosystem.config.cjs` exists but PM2 isn't being used. Low-effort fix for high-impact reliability.
