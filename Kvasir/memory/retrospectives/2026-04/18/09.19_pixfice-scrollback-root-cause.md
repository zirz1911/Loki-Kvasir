## AI Diary

There's a particular shape of bug that I find harder to catch than it should be: two implementations of the same thing, one correct and one not, living in the same codebase. The `capture()` function in `ssh.ts` was correct — it used `-S -${lines}`, it was called with 500 lines, everything was right. And I had read that code carefully. I had verified the server was sending 500 lines. The content was genuinely there in tmux's scrollback.

But that code path was never being used for the Pixfice terminal. The CapturePane connects to `/ws/pty`, which routes to `pty.ts`'s own `startCaptureLoop`. And that function had its own, simpler tmux invocation that nobody had updated. Two capture implementations, both trusted to be correct because one was correct. The other was just the bare minimum that was never revisited.

What makes this hard to catch in code review is that both implementations look reasonable in isolation. `tmux capture-pane -p -e -t target` is valid — it runs without error, returns real terminal content, does exactly what it says. You wouldn't look at it and say "this is wrong." You'd need to know what it's supposed to return versus what it does return.

The debugging path I took was good: I verified the content exists in tmux, verified the server code sends it correctly, checked the DOM structure for overflow traps, then finally traced the actual code path from CapturePane to the WebSocket to the server handler. That last step — following the actual call path rather than assuming which handler was responsible — was what cracked it. The lesson is old but keeps being true: when something "doesn't work" despite the obvious fix being in place, find the actual code path being executed, not the one you think is being executed.

The fix was one line. Two arguments. The bug had survived four previous fix attempts across multiple sessions because all four were fixing the right symptom in the wrong place.

## Lessons Learned

**When "server sends correct content" but client shows wrong content — trace the exact WebSocket path.** Two server handlers (`/ws` and `/ws/pty`) existed; both dealt with capture; only one used `-S -500`. Following the code path from CapturePane's `new WebSocket("/ws/pty")` → `handlePtyMessage` → `startCaptureLoop` revealed the divergence immediately.
