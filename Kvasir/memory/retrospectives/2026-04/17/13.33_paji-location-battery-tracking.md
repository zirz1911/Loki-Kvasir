## AI Diary

I came in clean — `/clear` at the start, nothing carrying over from a previous session. Lokkji said "ทำ Paji Location ต่อ ผมมีอะไรอยากแก้" and I had to find the repos first. Four repos. Found them fast.

The actual problem was more subtle than it looked. When I read `webhook.py`, I didn't see any explicit location deduplication. But git commit is the natural gatekeeper — if nothing in the CSV changes, commit returns non-zero and we silently skip the push. That's the "skip when location doesn't change" that Lokkji described. It's implicit, not explicit. The code doesn't say "if location same, skip" — git just refuses to commit identical content.

But battery was already in the CSV! So why wasn't it being picked up? The key insight: if OwnTracks sends the same event (same `tst` field) multiple times — a retry scenario — and battery happened to be the same too, then current.csv is literally byte-identical. Commit fails. No push. Battery data silently lost.

The fix is clean: read the current state first, compare, make a smart decision. Location changed → full update. Battery changed but location same → lightweight update (skip geocoding, skip history, just update current.csv battery and push). Nothing changed → truly skip.

I like this architecture because it's explicit now. Before, the "skip" was a side effect of git commit behavior. Now it's stated: `print("[username] skip — no change")`. The intent is in the code, not hidden in a return code.

The PM2 restart was smooth. Logs confirmed startup clean. I should note: `location-webhook` has had 5 restarts (↺ counter). That's worth watching — it may be crashlooping on certain payloads. Not investigated today.

## Lessons Learned

**When server code "skips" unexpectedly — trace git commit return codes, not just logic branches.** Silent failures in git (nothing to commit) look exactly like intentional skip logic from the outside. The fix is to make intent explicit in code.
